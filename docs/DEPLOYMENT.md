# Deploy the full single-user app on Render

This deployment runs the complete Python application behind Caddy, with one password-protected workspace and one persistent SQLite disk. It does not add participant accounts. Render terminates HTTPS; only Caddy's port is exposed. The Python backend remains bound to loopback inside the container.

## What the Blueprint creates

- One Docker web service on the Starter plan, one instance.
- A 1 GB disk mounted at `/var/data`, with SQLite at `/var/data/calibrated_ops.sqlite3`.
- A generated secret named `CALIBRATED_PASSWORD` for the fixed login name `admin`.
- `/healthz`, an unauthenticated availability check that returns no workspace records.

Render's service and disk are paid resources. Review the current price in your account before confirming creation. Without the disk, filesystem changes can be lost during restarts or deploys. See [Render disks](https://render.com/docs/disks) and [Blueprints](https://render.com/docs/infrastructure-as-code).

## Deploy

1. Sign in to Render, choose **New > Blueprint**, and select `Dhara092005/CalibratedOps`. Authorize repository access if needed.
2. Select `main` and the root `render.yaml`. Review the service, disk and charges before creating the resources.
3. Wait for the build and health check to pass. Render supplies `RENDER_EXTERNAL_URL`, which the app uses as its exact allowed HTTPS origin.
4. Open the service's HTTPS address. Retrieve `CALIBRATED_PASSWORD` privately from its Environment settings and sign in with username `admin`. Do not put this password in chat, source code, or screenshots.
5. Verify the incident queue, all three public datasets, a review write, and Research readiness. After a restart, verify the saved write is still present. Avoid live provider calls during this check.

The app imports the three bundled public collections idempotently on startup: 28 provisional cases, with no fabricated reviews, trials, or scores. Set `CALIBRATED_SEED_PUBLIC=0` before startup to disable seeding. Hosted data starts separately from the local workspace. Local reviews, participant records, and backups are not uploaded by a Git deployment.

## Environment settings

| Variable | Purpose |
| --- | --- |
| `PORT` | Public container port; Blueprint uses `10000`. |
| `CALIBRATED_DATABASE` | Absolute database path under the persistent disk. |
| `CALIBRATED_PASSWORD` | Required secret, 16–72 UTF-8 bytes, no newlines. Generated by the Blueprint. |
| `CALIBRATED_PUBLIC_ORIGIN` | Optional exact HTTPS origin, without a trailing slash; overrides `RENDER_EXTERNAL_URL`, for example when using a custom domain. |
| `CALIBRATED_SEED_PUBLIC` | `1` by default; imports the bundled provisional public datasets. |
| `OPENAI_API_KEY`, `OPENAI_MODEL` | Optional live generation settings; configure only if needed. |

`CALIBRATED_LOCAL_TEST=1` permits an HTTP loopback origin only for isolated local Docker tests. Never enable it for a hosted service. Credentials remain required even in the test mode.

Caddy hashes the secret via stdin and keeps its configuration in memory. The plaintext password and OpenAI key are not passed to the gateway child process. All workspace pages, scripts, APIs and exports require authentication; only health is public. Host and origin checks plus the existing review token remain enforced. Use a unique strong password and the HTTPS URL. This is low-volume single-user hosting, not a multi-user production research service or an institutional identity system. Basic authentication has no application logout button; close the authenticated browser session when finished.

## Validate locally

```powershell
python -m unittest discover -s tests -v
docker build -t calibratedops:deploy-test .
python tests/docker_smoke.py
```

The Docker smoke test uses a random test password, a loopback-only port, a temporary QA volume and synthetic evidence. It checks unauthenticated rejection, hostile host/origin rejection, authenticated API writes, bundled dataset import, and persistence after restart. It removes only the test container and volume it creates.

## Operations and backups

Keep one instance: the disk cannot provide a shared database to independently scaled replicas. A disk-backed deployment can have restart downtime. Keep the service and disk together; a deleted disk is not restored by pushing the repository again. Use Render's disk snapshots and a tested SQLite-aware backup process before migrations. Exports contain selected records and are not a complete database backup. Do not put backups or responses in the public repository.

When using a custom domain, set its exact HTTPS origin before starting the app, then verify writes through that domain. Origin mismatches reject writes deliberately. If startup fails, verify the origin, password length, disk path and build logs; do not remove authentication to work around a failed deployment.
